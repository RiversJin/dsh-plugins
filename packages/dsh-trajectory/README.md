# dsh-trajectory

最多保留一个工作锚点与一个临时查阅锚点；模型每次只操作当前活动层。

独立的 DSH 插件，让当前模型自行决定何时收束一段轨迹，并亲自写摘要。兼容 DSH `0.1.7-rc.2`，无需额外摘要模型或修改 DSH 核心。

## 自动补建锚点（0.2.1）

设置 `autoAnchorToolCalls: 2` 后，无活动工作/查阅锚点时，累计两次已完成的工具调用便在下一次模型请求前自动补建工作锚点。默认 `0` 关闭。锚点管理的四个工具不参与计数；同组多个调用分别计数，PTC 按实际子调用计数且不重复计算外层容器。计数可跨对话轮次；第一次计数的完整 assistant 工具消息组成为起点。

补建只追加原生元数据和模型可见通知，记录真实 ID，不往历史中插入或改写事件。只从策略首次启用后开始计数，启用标记持久化，重启后可以继续累计。创建、恢复或收束锚点后从新边界开始；已有工作/查阅锚点保持不变。不跨系统消息或拆开未完成工具组。摘要、归档和收束仍由当前模型决定并执行。

## 使用规则

- 工作锚点先收束，才能创建新的工作锚点。已有锚点时再次调用 `trajectory_anchor` 返回当前锚点及提示，不替换 ID、名称、起点或已读范围。查阅期间先总结或取消查阅标记，恢复底层工作锚点后再决定是否收束工作。
- 模型自主选择时机和摘要内容，没有强制轮数、时间、长度或压缩比例。
- 压缩前将原始事件完整保存到独立的 gzip JSON 归档，同步落盘并校验后再替换上下文。
- 成功压缩工作阶段后清除锚点；成功压缩查阅阶段后自动恢复挂起的工作锚点。下一次模型请求前移除已完成的压缩调用及结果。摘要标题、归档清单和返回元数据不再携带已退休的锚点 ID 或名称。保存失败、无效范围、过期锚点或取消时不替换原文。
- `trajectory_read` 首次成功读取归档时自动建立查阅锚点；已有工作锚点挂起保留。后续读取复用仍然有效的查阅锚点，失败读取保留原状态。查阅范围包含期间的新对话及其他操作，摘要必须一并保留相关的新要求和结果。
- 读完后可以继续阅读、总结压缩，或调用 `trajectory_release` 取消查阅标记并保留全部原文及期间的交流。后两种选择均恢复底层工作锚点。
- 已读范围按当前工作锚点、归档身份与校验和记录，位置采用实际返回文本的 UTF-16 半开区间。默认读取只提供请求中的未读部分；全部已读时返回提示与当前原文/摘要位置，不新建查阅锚点。`recover_detail`（补回细节）和 `reinterpret`（重新理解）配合简短 `focus` 可再次获取原文。
- 原始会话日志与归档均保留。清除锚点不会删除归档；会话恢复后可继续使用，分叉可以读取其继承的归档引用。已读记录仅在同一工作锚点及其原文/摘要仍有效时用于提示。

## 工具

| 工具 | 参数 | 行为 |
| --- | --- | --- |
| `trajectory_anchor` | `label` | 没有活动锚点时创建工作锚点；已有锚点时返回它并提示先收束，不创建替代锚点 |
| `trajectory_compact` | `anchor_id`, `summary` | 只接受活动锚点，摘要替换范围后返回归档与恢复的工作锚点（若有） |
| `trajectory_read` | 可选 `archive_id`, `offset`, `max_chars`, `intent`, `focus` | 列出归档及状态，读取未读范围，或带关注点重读；返回原文时准备或复用查阅锚点。0.2.4 起原文以对话稿形式分页：按上下文消息顺序给出序号、时间、说话者、正文、推理、工具调用参数与工具结果（失败标 ERROR），不含 replayState、thinkingSignature、request/header 与 step 事件；归档文件本身仍保存全部原始事件。非 UUID 的 `archive_id`（如 conversation_search 的 `archive_…`）会被明确指出不属于本工具 |
| `trajectory_release` | `anchor_id` | 取消当前查阅标记，保留原文和期间交流，恢复底层工作锚点 |

读取默认请求 16000 个字符，可按 `nextOffset` 继续读取，或用 `nextUnreadOffset` 定位本工作尚未读取的位置；指定 `max_chars` 可调整。部分已读时，返回请求中第一个未读连续区间，再按返回位置继续。工具不会静默丢弃归档尾部。归档引用只能来自当前会话或其继承历史，不能通过工具读入其他会话的任意文件。

模型使用说明由系统提示注入；当前锚点状态通过原生动态上下文提供，内容变化时才更新。说明建议按交流节奏收束一段对话，保留共同经历、偏好与更新、表达过的情绪、重要片段和开放话题；操作或精确细节在有需要时保留。查阅摘要同时承接刚才已经回看的内容与当前话题，帮助模型直接接话。不会强制模型调用压缩工具。

## 安装与挂载

构建后作为独立 npm 包安装。可以在需要此能力的 agent preset 中挂载：

```yaml
- id: trajectory
  name: dsh-trajectory
```

包也带有 `cordis.patch.yml` bundle，适合明确需要全局启用的部署。挂载到单个 preset 时，工具与提示只属于该作用域，不会自动添加到所有其他代理。

默认归档目录是 `$DSH_HOME/trajectory-archives`（默认 DSH home 为 `~/.dsh`），可用 `archiveDir` 指定绝对路径。归档文件按会话哈希分目录、UUID 命名，权限为 `0600`；备份会话时也应备份此目录。插件不执行过期清理。

## 边界与恢复

锚点从当前工具组的 assistant 消息开始，因此读取的工具结果也包含在范围内。允许在同组按顺序“建工作锚点—读取”，包括嵌套 PTC；两者起点重合时，压缩查阅后把原工作锚点起点迁到新摘要，保留 ID、名称和已读记录。模型先收到原文，再在后续请求中决定摘要；同组“读取—压缩”仍不能提前替模型总结尚未收到的内容。

压缩执行时先替换此前完整的调用和结果；当前工具组执行完成后，在下一次模型请求前一并清理其压缩调用。原始 system prompt 始终保留。

同组其他调用、结果及图片/文件引用保留为完整的历史记录。嵌套 `run_code` 保留其余代码和输出，移除旧锚点标识；同组刚创建的新锚点会调整起点并继续生效。用户或模型自行在正文中引用的文字不会被按锚点名称全局删除。

清理使用原生 surface 替换，不修改原始会话事件和归档。重启后会在下一次模型请求前补做尚未完成的清理，包括 0.1.0 遗留的摘要标题和压缩调用。主动读取原始归档时仍会得到其中的原始锚点记录，这些读取内容受新的查阅锚点覆盖。

另一个压缩或重试如果覆盖锚点起点，该锚点会失效。只覆盖查阅起点时恢复仍有效的工作锚点；覆盖两层起点时两层都失效。

锚点与归档清单保存在带插件来源的原生 session 消息元数据中，按事件投影重建。摘要替换使用原生 surface 协议，即使卸载插件，会话及已压缩摘要仍然可读。外部文件保存成功但提交前取消时，可能保留一个未引用的归档文件；不会丢失原文。

已读记录只在成功的原文结果真正进入原生会话后激活；嵌套调用需把原文页作为 JSON 结果传回根调用。插件验证最终渲染内容包含对应原文页，未明确传回的文本保守地不记为已读。查阅摘要以元数据承接被替换原文的范围；重试或其他上下文替换移走凭据时，记录失效。取消查阅保留原文及记录；收束工作后清除该工作的去重状态。程序只证明文本曾提供及其当前保留形式，不判断模型是否理解，也不保证摘要包含原文每个细节。

## 双层锚点实验结果（2026-10-03）

隔离分支使用真实 `deepseek-official/deepseek-flash`、`high` 推理强度，通过原生 Agent 循环决定和执行工具。程序只准备合成旧归档，不替模型选择评估阶段的工具或摘要。三个场景共 28 次模型请求，另用已安装的单锚点 0.1.1 做了 5 次请求的隔离对照。前置实验 24 次请求因测试环境在原生 system head 之前插入归档引用而不计入正式端到端评分；修正测试环境后保持原型及任务提示不变重跑。

三个正式场景均完成了工作锚点保留、查阅锚点复用、正确查档、保留中途新增要求、收束查阅后恢复原工作锚点；其中覆盖多归档分页和运行时重建后恢复原会话。20 项本地运行时测试通过，正式模型会话也全部通过原生严格格式回放。

端到端结果尚未通过：三个场景在正确压缩主线后都新建了工作锚点，单锚点对照也复现。有效上下文证据显示，要求结束本阶段的最新用户消息被压缩，而最初要求建立工作起点的消息仍可见；完成的压缩调用和结果也已移除。需要先解决当前请求在压缩后的保留或完成状态衔接，再考虑上线。此小样本不能证明 K3 必然通过。

下文提到的 `evaluation/*` 与付费实测脚本的输出是实验记录，保存在仓库之外，未随本仓库发布。

结果摘要见仓库根目录 `evaluation/assessment.json`，边界分析见 `evaluation/context-boundary-analysis.json`。付费实测脚本为 `tests/deepseek-eval.mjs`，不会随 `npm test` 运行。它只在运行时从现有凭据文件读取 DeepSeek 密钥，结果文件不保存密钥；使用隔离的 `DSH_HOME` 和 `TRAJECTORY_EVAL_ROOT`。设置 `TRAJECTORY_EVAL_CONTROL_ONLY=1` 可运行已安装单锚点版本的隔离对照。线上插件、会话与服务未修改。


### 提示词复测与测试设计复核

进一步的隔离复测只调整提示词与摘要旁的说明，未改锚点状态机或压缩范围。三轮多轮场景分别通过 0/3、1/3、2/3，尚不能认定修复完成；每轮 20 项本地运行时测试通过。

新增 `TRAJECTORY_EVAL_AUTONOMOUS_ONLY=1` 模式，只给一次规划目标，让模型自行决定查阅和收束。三轮均自主完成了查阅收束并交付清单；首轮自动检查因要求整句逐字匹配而误判午餐限制，保留原始失败报告，后两轮使用允许 Markdown 和同义表达的约束检查通过。这些自然任务均未自行建立工作锚点，因此只覆盖自主查阅收束，不覆盖自主双层锚点使用。未对生成清单的所有细节做完整事实评分。

复核发现原分阶段任务先要求“暂时不用读取旧档案，也不用收束”，后面又多次限制阶段边界；压缩后初始限制仍可见，而解除限制的后续要求进入摘要。原始插件说明还将新生成摘要与旧档案统一称为非当前指令。测试设计和提示词可能共同干扰结果，应先审查初始提示，再以自然自主任务与多轮变更任务分别验证；不能把这些结果单独归因于模型能力。当前说明仍为实验版本，未部署。

初始真实请求中的完整可见文本、工具定义、分阶段任务原文及复测结果见 `evaluation/prompt-review.json`。本轮 107 次真实请求，加此前 57 次合计 164 次；运行产生的原始结果均保留，未作为训练样本使用。


### 正向任务与接续提示（此前实测版本 a6125fc）

当前实测脚本以正向目标替换逐阶段的暂停/启动指令，测试三个场景：自主开始规划、已有工作中收到新要求、恢复已有查阅并接受后续修改。第二、三个场景的初始工作/查阅状态由测试环境准备，单独标注，不计作模型自主行为。补充要求使用原生下一步输入，并检查对应用户消息确实进入查阅摘要替换范围。任务结果与机制覆盖分别记录；保留工作锚点本身不算任务失败。

接续说明明确：工具插入的摘要承接被替换的对话，保存的用户更新仍是用户要求，较新的更新接替较早的版本；已核对事实与已完成操作继续作为当前进度。查档入口改为需要细节时可用，并说明查找事实应沿 `nextOffset` 覆盖未读范围。仍由模型自主选择推进、查阅、收束及交付时机。

最终这轮真实 DeepSeek 测试 3/3 场景通过，合计 19 次请求（6、7、6），无工具错误，严格格式回放均通过；20 项本地运行时测试通过。自由开始场景由模型自行建立工作锚点、进入查阅并收束查阅；其余两组保留了新要求并恢复原工作锚点。查阅中更新的场景由早期版本 20 次请求仍未完成，改善为这轮 7 次完成，仍有重复查阅，不能从单轮样本推断稳定成功率。

三组最终都由模型选择保留工作锚点，这轮自然任务未覆盖主线锚点最终收束；该操作仍由本地运行时测试覆盖。计划建议本身未做全面事实审校。原始失败记录、判分修正、各版比较及限制见 `evaluation/continuation-followup.json`。本阶段共 115 次真实请求，加此前 164 次累计 279 次；全部发生在隔离环境，未部署线上。

`TRAJECTORY_EVAL_AUTONOMOUS_ONLY=1` 只跑自主开始场景；`TRAJECTORY_EVAL_CASE=ongoing-work-with-update` 等可选择单个场景。`TRAJECTORY_EVAL_CONTROL_ONLY=1` 在隔离环境读取已安装单锚点插件，运行自主开始场景；与前述历史分阶段对照的任务不同。


### 长期陪伴对话的接续说明（当前实验版本）

根据使用定位，提示词调整为承接长期对话：保留共同经历、偏好与更新、表达过的情绪、重要片段、反复出现的话题和留待以后继续的线索。摘要帮助延续交流，允许转述、印象、联想、回顾和话题发散；需要精确细节时再按当前对话的需要处理。模型自主选择回看、收束或展开新话题的时机，开放的话题可以留待以后继续。

双层锚点、归档保存、区间替换和恢复规则保持不变；`work` 仍是持久化类型名，在提示中表示主线话题或共同活动。接续说明仍保留摘要中较新的用户更新接替较早版本，以及区分当前用户要求与旧档案引用的边界。摘要包装、动态状态和工具描述一并使用对话语境，避免继续暗示每段交流都要核验、完成和交付。

此前行程任务的 3/3 结果属于 a6125fc，不能算作当前陪伴措辞的真实模型验收。`deepseek-eval.mjs` 保留为特定任务接续的诊断脚本，不以其中逐项事实命中或任务收尾作为陪伴对话的总体质量标准。这版提示词通过 20 项本地运行时测试；随后进行了下述 K3 256 陪伴场景实测。修改保留在隔离分支，未部署。


### K3 256 陪伴场景实测（提示词基线 90c02ad）

`tests/kimi-companion-eval.mjs` 使用真实原生 Agent 循环、已安装的 PiAiAdapter 和 Kimi Coding provider，固定 `kimi-coding/k3-256k`，未加载自动升档插件。HTTP 请求体的 15 次模型选择均核对为 `k3-256k`；3 个合成场景、共 6 轮用户输入均完成，工具无错误、严格会话回放通过、原生回放无降级。起初模型描述字段层级的校验错误发生在零模型请求阶段，修正后完整结果单独保存。

自由回忆场景能从雨天等车和月亮邮局接到当下的疲惫，再自然联想到小熊留下的灯；已有工作锚点的场景能接住查阅中的轻快转题，并收束查阅、恢复原主线；预置查阅摘要恢复后的场景能直接沿海边画面继续，并扩展沙滩上的月亮邮局。创造性补充按陪伴定位人工审阅，不以逐字复述或事实关键词命中作为总体质量判分。

仍有重复回看：前两组各把两份档案读了两次，也各收束查阅两次；第一组公开进度出现了重复的“翻完/收好”。第三组的收束由环境预置，模型两次实际回复都未调用工具，因此它验证的是恢复后的自然接续，不代表模型自主选择了该次收束。没有填满 256K 上下文，也没有加载完整线上祈月人格、记忆与私人历史。

结果见 `evaluation/kimi-companion-assessment.json`；可直接 review 的用户输入与模型公开回复见 `evaluation/kimi-companion-transcript.txt`。运行脚本须显式执行，不包含在 `npm test`；支持 `TRAJECTORY_EVAL_ROOT` 和 `TRAJECTORY_EVAL_CASE`。本轮未修改提示词或部署线上。


### 加强回看后的接续说明（当前实验版本）

总提示进一步说明：摘要记载的回看已经发生在同一段交流中，应结合这份记录理解较早的回看邀请；已经读到的画面、感受和细节可以直接用于下一次回应。新的好奇、想深入的细节或新的回忆邀请仍可引出进一步查阅。摘要参数提示模型写下已经回看什么、交流转向哪里；只有查阅摘要附加对应接续说明。双层锚点和区间算法不变。

沿用上一轮三个 K3 256 场景、六轮用户输入；通过 `TRAJECTORY_EVAL_ARCHIVE_FIXTURE_ROOT` 从上一轮复制两份原始合成归档，复制前后验证校验和，保持归档内容完全相同。未使用此前模型生成的回看摘要作为新测试材料，也未改变聊天输入或增加场景。

### 工作锚点、已读范围与 DeepSeek 实测（2026-10-04）

本轮新增范围记录、取消查阅和带意图的重读，工具说明使用工作语境；工作可以是一段聊天或共同活动，不要求建立目标对象。未收束的工作锚点不能被新锚点替换；重复申请返回现有状态。同组建工作锚点并查档现已支持，重合的起点在查阅压缩后接到新摘要，保留工作身份和范围记录。

使用真实 `deepseek-official/deepseek-flash`、`high`，原生 Agent 循环自主选择工具。三组陪伴输入和两份原始合成归档与此前一致，另用两条正向续问观察补细节、重新理解；没有增加负样本或把失败轨迹喂给模型。基线 9 次请求；首轮原型 15 次，其中自由回忆遇到旧的同组调用限制，该记录完整保留；边界和工作锚点规则修正后三组共 9 次，均无工具错误并通过严格回放。自由回忆实际同组调用了 `trajectory_anchor` 和两次 `trajectory_read`，随后直接交流；查阅中转题组总结后恢复工作，摘要后恢复组直接继续对话。

两条正向续问另用 8 次请求：围巾位置选择 `recover_detail`，缓冲带含义选择 `reinterpret`，均附有对应关注点；后者随后调用 `trajectory_release` 保留原文并恢复工作。工具与严格回放全部通过。补细节组先压缩了原文，下一轮提出保留原文时只口头答应、没有再取回整页，这一点保留为模型状态理解的观察项。最终设计两轮实测合计 17 次、本次实验累计 41 次请求；实际请求体均为 `deepseek-flash`。

最终 25 项本地测试和 typecheck 通过，新增验证均为正向生命周期：同组建锚点与查阅、摘要迁移后恢复和继续收束、同一工作中的范围提示、部分重叠分页、Unicode 边界、两种重读及原生恢复。阻止替换未收束工作、同起点查阅压缩和已读短提示由本地运行时测试验证，本轮真实模型未主动覆盖这些全部分支。付费实测后补齐了无工作锚点不返回去重指针、空尾页保持锚点的分页处理，并重跑全部本地测试；实测中的读取均有工作锚点且非空，不受此补充影响。

这仍是小样本：基线本轮也没有重复回读，不能据此声称请求减少、理解稳定或达到线上验收。范围记录表示原文曾提供及其当前保留形式，不证明理解程度或摘要完整性。报告与公开对话见 `evaluation/deepseek-read-ranges-assessment.json`、`evaluation/deepseek-read-ranges-transcript.txt`。

### 自然续聊中的重复读取观察（2026-10-04）

用户选择只观察自然对话，不预置重复行为。因此保持插件实现 `2977b41` 不变，沿用原三组场景与合成归档，每组在原两轮之后追加两条自然续聊。原有场景的工作/摘要准备和中途转题仍明确标注，评估阶段全部由真实模型自主决定工具；没有构造默认重复调用，也没有追加纠正提示。

三组共 12 轮交流（转题组另含原场景的一次中途插话），18 次真实 `deepseek-flash/high` 请求，全部正常结束，无工具错误，严格会话回放通过。四次原文读取在当前工作中属于首次提供，另一次是恢复组第四轮带关注点的 `recover_detail`，随后正常总结并回应。没有默认重复返回原文，也没有连续重复查阅的循环。自由回忆组首次查阅虽使用 `reinterpret`，但原文在本工作尚未提供，统计上没有误记为重复读取。

自由回忆组实际同组创建工作锚点并读取两份原文，然后由模型自主总结查阅；工作锚点 ID 保留、起点从共同的事件序号 20 接到摘要事件序号 36，第三次模型请求已读取此状态。后续三轮都直接回应，补上了真实模型自主完成同起点查阅收束的覆盖。转题组总结后也连续三轮直接交流。

**覆盖限制：** 本轮 `already_read` 返回和模型实际接收次数均为零。因此只能说明这轮自然对话未复现默认重复读取，不能算作“收到已查阅提示后是否继续反复调用”这一分支的验证，也不能据此断言长期彻底解决。没有为了命中分支加入用户未允许的预置重复行为。

结果及逐轮工具顺序见 `evaluation/deepseek-natural-repeat-assessment.json`，用户输入与公开回复见 `evaluation/deepseek-natural-repeat-transcript.txt`。设置 `TRAJECTORY_EVAL_NATURAL_REPEAT=1` 可单独运行这组观察，不能与 `TRAJECTORY_EVAL_READING_INTENTS=1` 同时使用。本轮仅修改实验脚本和记录；插件源码及已构建文件的校验和与运行开始时一致，未改线上。


### K3 256 同场景自然续聊（2026-10-04）

按用户要求，以 `kimi-coding/k3-256k`、`high`、8192 输出上限运行同样三组四轮自然对话。没有加载自动升档插件；元数据及模型解析均确认 262144 上下文窗口，19 次实际 HTTP 请求体的模型均为 `k3-256k`。与 DeepSeek 观察逐项核对了全部用户输入、陪伴说明、场景准备和原始归档校验和；与昨晚 K3 记录核对了相同的前两轮输入和归档。没有预置重复调用或追加纠正提示，插件实现仍为 `2977b41`。

三组共 12 轮交流、19 次真实请求（6、7、6），全部正常结束，工具错误为零，严格回放通过，PiAiAdapter 回放降级为零。自由回忆组同组建工作锚点并读两份原文，随后总结查阅并恢复同一工作锚点，后续三轮直接接话。转题组读取两份原文，先总结查阅、再总结工作，各一次，之后三轮直接接话；这两个压缩分别对应不同层级。恢复组前三轮直接交流，第四轮用户邀请接续小熊画面时，模型带着具体关注点以 `recover_detail` 回查一次，之后调用 `trajectory_release` 保留原文并恢复工作。

按实际范围统计，四次读取是当前工作首次提供原文，一次是带关注点的重读；默认重复原文和 `already_read` 返回均为零。昨晚恢复组相同的前两轮曾先回查并压缩一次，使用 4 次请求；本轮相同前两轮直接回应，只用 2 次请求。这是同一模型标识下的改善迹象，但仍是单次观察，不能分离各项改动与生成波动，也没有覆盖收到 `already_read` 后是否继续重复调用。

报告见 `evaluation/kimi-natural-repeat-assessment.json`，公开对话及工具顺序见 `evaluation/kimi-natural-repeat-transcript.txt`。`tests/kimi-companion-eval.mjs` 现支持与 DeepSeek 脚本一致的 `TRAJECTORY_EVAL_NATURAL_REPEAT=1`、新目录保护和实际请求状态记录。没有填满 256K 上下文或加载线上的完整人格与私人历史；本轮仅更新实验脚本与记录，未部署。

## 自动锚点不再跨越纯对话（0.2.3）

自动补建的计数只在连续的工具片段内累计：一轮已完成、含真实用户消息且没有任何工具调用的对话会清空当前候选，下一次工具调用重新从零开始计数。定时消息、时间上下文等非用户来源的安静轮次不清空候选，用户参与且带工具调用的轮次也不清空。此前两次相隔数小时的零星调用（例如定时 tick 里的掷骰子）会把中间整晚的对话一起圈进一个锚点，模型若按"只是工具调用"的印象一句话收束，这段对话就会在上下文里消失。

自动锚点通知现在附带覆盖范围：起止时间、时长、上下文消息条数和其中的用户消息条数，并明确说明 `trajectory_compact` 的摘要会替换范围内的全部内容，提醒模型把范围内的对话一并写进摘要，而不是只写工具工作。

## 自动锚点的一次性收束提示（0.2.2）

可设置 `autoAnchorReminderTurns: 5` 与 `autoAnchorReminderMinutes: 60`（默认均为 0，关闭）。仅自动补建的工作锚点参与检测：连续超过 5 轮已完成的真实用户无工具对话，或创建满 60 分钟，向原主模型投递一次收束请求。任何实际工具调用会重新计算连续无工具轮数；小时上限从锚点创建时起算。后台空闲检查也覆盖无人继续聊天的时间条件。

同一锚点只投递一次，两个条件、重复检查、重启及梦前流程共享持久化的请求记录。提示后仍未收束就保持等待，不循环催促；实际收束必须由模型调用工具完成。新的锚点 ID 才有新的提示额度。此功能需要 DSH schedule 服务；`trajectoryClosure.request(agent, reason)` 提供同一会话内串行、可去重的内部交接入口。

在 agent preset 内部署时，trajectory 与 dream-context 两个插件条目必须使用同一个命名隔离域，例如都配置 `isolate: { trajectoryClosure: companion-trajectory-closure }`，并保留各自已有的其他隔离项。使用 `true` 只会建立插件自己的隔离域，无法让梦前流程取得共享协调器。
